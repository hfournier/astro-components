# Documentation format and prop-manifest convention

> **Superseded in part by ADR-0010**: point 1 (one `documentation.mdx` file per component) is replaced by a three-file split (`documentation.mdx` + `usage.mdx` + `example-*.mdx`), and point 4's frontmatter schema gains a required `meta` object and renames `title` to `name`. Everything else below (points 2-3, 5-9, 11, and the `components` collection rename in point 10) still stands.

Each component folder already co-locates `<Name>.astro` and `<Name>.spec.ts`; a per-component `examples.mdx` was added alongside them with `{title, description}` frontmatter and an MDX body of live rendered examples, but no per-prop documentation exists anywhere for a human or a coding agent to consult before using a component. This decision defines that convention, building on the prop-naming convention (ADR-0001) and accessibility standard (ADR-0003). We decided:

1. **`examples.mdx` is renamed to `documentation.mdx`**, one file per component rather than a separate `examples.mdx` + `documentation.mdx` pair. The examples-vs-docs boundary would be perpetually fuzzy — examples are themselves documentation for a human — so splitting them invites the same content to be filed inconsistently across components.
2. **The frontmatter/body split is by data shape, not audience.** Frontmatter carries structured, machine-checkable facts (consumed equally by a rendered props table for humans and by an agent); the MDX body carries prose and live rendered examples that only make sense read in order. This is a deliberate correction of the "frontmatter for agents, body for humans" framing the idea started from — an agent reading the file sees the whole file, and a human benefits from structure too.
3. **Prop docs are hand-authored and Zod-validated, not derived from the component's actual `Props` type.** Generating them would need real TypeScript type-checking tooling this decision doesn't build. The accepted drift risk is offset by an automated check (point 11).
4. **Frontmatter schema**, minimal to start and extended only when a real component needs more:
   ```yaml
   title: string
   description: string
   role: "primitive" | "pattern" # see point 8
   props: # optional
     - name: string
       type: string # literal type as written, e.g. '"solid" | "outline"'
       required: boolean
       default: string | null
       description: string
   slots: # optional, one entry per named or default <slot>
     - name: string
       description: string
       kind: "any" | "text" | "component"
       # when kind is "component":
       component: string # e.g. Tab
       multiple: boolean # one instance vs. one-or-more
   cssProps: # optional, for consumed CSS custom properties / role tokens
     - name: string # e.g. --radius-control
       description: string
   extends: # optional, see points 5 and 7
     kind: "element" | "component"
     tag: string[] # when kind is "element", one or more tag names, e.g. [button]
     name: string # when kind is "component", e.g. BaseOverlay
   parents: string[] # optional, see point 9 — components this one may only be used inside
   ```
5. **Only a component's own declared props are listed** — never props it only exposes by composing another component. Dialog's `Props` is just `type Props = BaseOverlayProps`, so Dialog documents zero own props and sets `extends: { kind: component, name: BaseOverlay }`; Popover documents only its one own prop (`showCloseX`) and also sets that same `extends`. See `CONTEXT.md`'s **Own prop**. Resolving the full inheritance chain would need real type-checking (a `ts.Program`) rather than a cheap syntactic parse of each file's own `Props` declaration, which this decision deliberately avoids.
6. **A slot's accepted content is a `kind`, not free text.** `"any"` (arbitrary content — Dialog's `header`/`footer`, Popover's default), `"text"` (plain text only), or `"component"` (the slot only accepts one or more instances of a specific named sub-component — a discriminated union, since `"component"` requires the companion `component`/`multiple` fields the other two kinds don't have). Tabs' default slot is the motivating, already-real case: `Tabs.astro` only does anything sensible with `Tab.astro` instances (each rendering a `data-hfdev-tabpanel` marker Tabs' build-time walk looks for), so its manifest declares `kind: component, component: Tab, multiple: true` rather than describing that constraint in prose. See `CONTEXT.md`'s **Component slot**. This is expected to be a common pattern as more components compose fixed child types (list-like components, item collections), not a one-off for Tabs.
7. **`extends` is a discriminated union on `kind`, not a bare string.** `{ kind: element, tag: string[] }` (a component whose `Props` extends `HTMLAttributes<tag>`, e.g. Button's `tag: [button]`) or `{ kind: component, name: string }` (a component composing another documented component, e.g. Dialog/Popover's `name: BaseOverlay`) are not interchangeable: the first has no further documentation to follow (just "standard `<tag>` attributes also apply"), the second points at another component's own manifest for the props it doesn't declare itself (point 5). A bare string can't distinguish "dead end" from "follow this link," which a renderer or an agent both need to know. This reuses the same `kind`-discriminated shape as `slots` (point 6) rather than introducing a third way of modeling "one of a few kinds" in the same schema. `tag` is an array, not a single string, because a component can genuinely extend more than one native element: BaseOverlay's `Props` is `HTMLAttributes<"dialog" | "div">` (it renders one or the other based on its own `as` prop), so its manifest is `tag: [dialog, div]` rather than embedding a pipe-delimited union inside a string — which would just relocate the "prose, not data" problem point 2 already rejected once.
8. **A required `role` field, not just prose, says whether a component is meant to be used directly.** `"primitive"`, `"pattern"`, or `"internal"`, reusing `CONTEXT.md`'s existing **Primitive component** / **Pattern component** terms plus a new **Internal component** term rather than inventing unrelated vocabulary. It's required (not optional like `props`/`slots`) because it's a fact about every component's fundamental nature, not an extension some components need and others don't. Classifying real components against the values exposed two gaps in the original two-value taxonomy:
   - `CONTEXT.md`'s **Pattern component** definition required "built on top of one or more primitives," but Button is a pattern component (used directly, not composed elsewhere) with no primitive underneath it. `CONTEXT.md` is sharpened to drop that requirement — a pattern component is defined by being used directly, not by what it's built from.
   - `"primitive"` alone conflated two different things once `TabList`/`TabPanels` were classified: `BaseOverlay` is a genuine reusable building block (composed by both Dialog and Popover, generic own props), while `TabList`/`TabPanels` are pure implementation details of `Tabs` alone — never composed elsewhere, and their own props (`labels`, `randomId`) only make sense in terms of `Tabs`' internal AST walk. Giving both the same role would tell an agent "don't use this directly" but hide the sharper fact that `TabList`/`TabPanels` aren't independently meaningful at all. A third value, `"internal"`, is added rather than stretching `"primitive"` to cover both cases. See `CONTEXT.md`'s **Component role** and **Internal component**.
9. **`parents` is the inverse of a `Component slot`, and gets its own field rather than being inferred.** `slots[].component` says what a component's slot accepts (Tabs → `Tab`); nothing said the reverse — that `Tab` may *only* be used inside `Tabs`. Both facts are useful independently: an agent looking at Tabs' docs learns what goes in the slot, but one looking at Tab's docs in isolation has no way to know it can't be dropped anywhere else, short of cross-referencing every other component's `slots` array to find who claims it. `parents: string[]`, optional (most components carry no such restriction), lists the documented components a component may be composed inside. Tab is the motivating, already-real case: `parents: [Tabs]`. Kept as a flat array of names, not a richer structure naming which slot specifically — no second real case yet demands that precision, and point 4's own rule is to extend the schema only when one does. See `CONTEXT.md`'s **Required parent**.

   `role: internal` components (point 8) reuse this same `parents` field for the same restriction, even though the mechanism differs — `TabList`/`TabPanels` aren't placed in a slot at all, they're imported and rendered directly by `Tabs`' own template. Introducing a second field (e.g. `internalTo`) to say the same thing — "may only be used inside this one component" — would just fork one fact across two field names depending on *how* the restriction arises, which the reader can already tell from `role` (a `pattern` component's `parents` points at a slot owner; an `internal` component's `parents` points at its sole renderer).
10. **The `examples` content collection is renamed to `components`.** `src/content.config.ts`'s glob moves from `**/examples.mdx` to `**/documentation.mdx`, and its Zod schema gains the required `role` field and the optional `props`/`slots`/`cssProps`/`extends`/`parents` fields above.
11. **The drift check lives in the existing Playwright suite, not a new test layer.** A single shared spec (not per-component) walks every component folder, parses each component's own `Props` type via the TypeScript compiler API to get the authoritative own-prop-name set, and diffs it against that component's `documentation.mdx` frontmatter — catching both undocumented and stale/removed props. It does no browser work, so it stays inside ADR-0002's "one test framework" call rather than reopening it for a separate Node-only unit-test layer. `typescript` is added as an explicit devDependency (already present transitively via `typescript-eslint`).

This is hard to reverse once agents and contributors start relying on a fixed filename and frontmatter shape to find "the docs" for a component, is surprising without context (why frontmatter holds structured facts rather than being agent-only; why inherited props aren't flattened in), and reflects a real trade-off between full type-derived accuracy and the cost of building that tooling now.

## Consequences

Spec-only for the schema and inheritance rule. Two concrete pieces of mechanical follow-through ship with this decision (not deferred, since they're renames/config rather than documentation content): `src/content.config.ts` and `src/pages/examples/{index,[id]}.astro` are updated for the `components` collection, and the three already-existing WIP files (`button/`, `dialog/`, `popover/`) are renamed to `documentation.mdx`, keeping their current `title`/`description` and an empty `props` array. Writing accurate prop manifests for those three, and retrofitting the other three components, stays out of scope per the map (issue #1), as does the drift-check spec itself (point 11) — tracked as separate fast-follow implementation work referencing this ADR, since it's an implementation task rather than a further decision. Tabs' `documentation.mdx` already has an accurate `slots` entry (`kind: component, component: Tab, multiple: true`) since it was the motivating case and the real `Tab.astro`/`Tabs.astro` composition it describes already exists — this is the one exception to "documentation content is out of scope," made because the schema change needed a real instance to validate against.
