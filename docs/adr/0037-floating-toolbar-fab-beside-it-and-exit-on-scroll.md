# The floating toolbar's FAB sits beside its toolbar, and it leaves on scroll by a transform

M3 Expressive's floating toolbar is a pill of contextual actions over the page's content, horizontal or vertical, alone or paired with a FAB, and it can animate off screen as the content scrolls (#212). It reuses the docked toolbar's colors and arrow keys (ADR-0036), which move to `src/utils.ts` as `toolbarColorClasses` and `moveFocusWithArrows`. A few things weren't settled by the docked toolbar. We decided:

1. **The FAB goes in a `fab` slot, outside the `toolbar` role, and `class` goes on the element holding both.** M3's Specs note that only Compose has a floating toolbar with a FAB: "On other platforms, each component needs to be added separately." So the FAB is a Fab beside the toolbar, not one of its controls. Tab reaches it after the toolbar's controls, and the toolbar's arrow keys stop before it. The component renders a wrapper around the toolbar and the FAB, which carries `data-ac-toolbar-floating` as other components' outer elements do, with the toolbar as its `toolbar` part (ADR-0020), laid out as Compose lays them out: 8dp apart (the FAB between-space token), the FAB centered on the toolbar, after a row and below a column. The page places the pair, so `class` goes on the wrapper and every other attribute on the toolbar. The wrapper gives the FAB M3's elevation level 1 (raised to level 2 on hover and back to level 1 while pressed, as a FAB's states move it), with `!` so it beats the Fab's own level 3 and 4. The FAB's color, secondary container beside a standard toolbar and tertiary container beside a vibrant one, is the Fab's own `color` prop, which the docs and examples set. The toolbar can't read the props of what's slotted into it, and recoloring a Fab from outside would silently override a `color` the page chose.
2. **A vertical toolbar is `orientation="vertical"`, set as `aria-orientation`, and moves with the up and down arrows.** This follows Divider and Slider, whose `orientation` prop also sets `aria-orientation`. `moveFocusWithArrows` reads the attribute, so a vertical toolbar takes up and down, which don't mirror right to left. The docked toolbar has no `aria-orientation`, so its keys don't change.
3. **`scrollBehavior="exit-always"` moves the toolbar out of its scroll container's view with a transform.** This is Compose's `exitAlwaysScrollBehavior`. As in AppBar (ADR-0034), one capture-phase scroll listener runs once a frame. It finds each toolbar's scroll container with `scrollerOf`, and checks with `pinnedOf` that the toolbar is pinned, by `sticky` or `fixed` on itself or an ancestor. Both helpers move to `src/utils.ts` from AppBar. When the container scrolls down, the wrapper gets an inline `transform: translate(…)` that takes it past the nearer edge of the container's view, plus 16px so its shadow leaves too: the top or bottom edge for a row, the start or end side for a column. Compose instead takes the exit direction as a parameter. Scrolling up clears the transform. A resize recomputes it for a toolbar that has left, since the view's edges move. The wrapper's `transform` transitions on fast spatial, Compose's floating toolbar animation spec, and only under `motion-safe`. The transform composes with a page's own centering classes, such as `-translate-x-1/2`, which Tailwind sets with the separate `translate` property.
4. **A toolbar that has left comes back when one of its controls takes focus, and stays while focus is in it.** M3's Accessibility page asks that people keep access to the toolbar's controls while the content is scrolled. The toolbar stays in the tab order, rather than becoming inert, so Tab still reaches it and it comes back on `focusin`. Compose turns the scroll behavior off while touch exploration is on, which the web can't detect.

We rejected putting the FAB inside the `toolbar` role. That would make the arrow keys reach it and announce it as one of the toolbar's actions, where M3 treats it as a separate component on the web. We rejected moving the toolbar with the `translate` property, since a page's centering classes use it and an inline value would override them. We also rejected hiding a toolbar that has left with `inert` or `visibility: hidden`, which would take its actions away from keyboard users until the content scrolled back up.

## Consequences

- A Fab in the `fab` slot keeps whatever `color` the page gives it. A standard toolbar with a primary-container FAB is possible, though the docs show M3's pairing.
- Compose's collapse into a FAB on scroll, M3's third scroll behavior, isn't built. `scrollBehavior` can take another value for it later, but M3 asks that a toolbar not collapse and leave at once.
- Focusing a control of a toolbar that has left can scroll the page, as the browser scrolls the control into view before the toolbar comes back.
- The docked toolbar could take `scrollBehavior` the same way. ADR-0036 left hiding it on scroll for later.
