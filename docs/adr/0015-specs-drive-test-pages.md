# Specs drive the test pages, not the docs examples

> **Extends ADR-0011 §3 and updates ADR-0013 §2**: the `tests` collection now lives in `src/tests/` (not `src/data/tests/`) and holds the fixtures component specs run against, and specs move from `src/docs/<id>/` to `src/tests/`. ADR-0011's other decisions and ADR-0013's flat `src/components/` are unchanged.

Component specs tested components by visiting their docs pages (`/components/<id>`) and reaching into particular examples: the Usage block's first tablist, or a `code-preview` holding a given label. That tied two things with different jobs together. Examples exist to show a reader how a component, its props and its slots are meant to be used. Specs need markup chosen for the case under test, which often isn't good documentation. An example couldn't be reworded, reordered or removed without breaking a spec, and some examples were added only so a spec had something to target. The temporary Button examples for the MDX paragraph fix (#74, #77) were one case.

ADR-0011 already gave the site a `tests` collection: pages that show a component in many contexts, checked by eye, which it described as "not automated tests". That's the natural home for test fixtures, so we decided:

1. **Component specs drive `/tests/<id>` pages, never `/components/<id>`.** The one exception is the site-layout specs (point 5), which test the site's own chrome rather than a component's cases. Each spec's fixtures live on its component's test page, `src/tests/<id>.mdx`, rendered by `src/pages/tests/[id].astro`. Test pages keep ADR-0011's role as visual check-by-eye pages listed in the sidebar. They are now also the automated specs' fixtures, so ADR-0011's "They aren't automated tests either" no longer holds.
2. **`examples` and `usage` are documentation only.** They can be reworded, reordered or removed freely. Nothing is added to them to give a spec something to target, and an example that exists only to serve a spec is removed or rewritten as documentation.
3. **Each case on a test page is a `Section` with `data-testid="<page>-<case>"`**, where `<page>` is the test page's id and `<case>` is a kebab-case name for the case, usually its heading's text (`tabs-icons-and-badges`, `heading-level-3`). A spec scopes to a case with `page.getByTestId(...)`, so cases can be added, reordered or retitled without breaking specs that don't use them. We chose a test id over naming each `Section` by its heading (`aria-labelledby`, found with `getByRole("region", { name })`). That needs an id on every heading and ties a spec to heading text written for the person checking the page by eye.
4. **Cases that throw at render time get their own `.astro` page under `src/pages/tests/`.** A throw on an MDX test page fails the page and the build. Instead, the page renders each case in its own Astro container (`experimental_AstroContainer`), catches the error, and lists each case's outcome in an element with the case's test id. `/tests/tabs-content` is the first one (#75). Its fixture component sits in `src/tests/` beside the MDX page. Cases that must not sit in a `Section` get one too: an overlay's `<header>` and `<footer>` are generic inside a sectioning element and only become landmarks outside one, so `/tests/overlay-landmarks` (#131) places a modal Dialog, SheetSide and SheetBottom outside `<main>`. Its spec, `OverlayLandmarks.spec.ts`, covers all three and finds each by its accessible name, since there's no `Section` to carry a test id. A component a page can have only one of gets one too: the site's own NavRail isn't expandable, and a page has room for one rail, so `/tests/nav-rail-expandable` (#158) has its own layout, without BaseLayout, around an expandable rail. `NavRail.spec.ts` finds it by its navigation's name. Likewise, the site's rail and drawer have their own backgrounds, so `/tests/nav-drawer` (#160) lays out a rail and a NavDrawer on their default ones.
5. **Specs live in `src/tests/`, beside the pages they drive.** `src/tests/` holds the test pages (`<id>.mdx`), their specs (`<Name>.spec.ts`), fixture components, and the shared Playwright harness in `src/tests/support/` (`a11y-fixture.ts`, `helpers.ts`). `src/docs/<id>/` then holds documentation only, which updates ADR-0013 §2. No config change is needed: the `tests` collection only loads `**/*.mdx`, and Playwright's `testDir` is `./src` with `testMatch: "**/*.spec.ts"`. The site-layout specs (NavRail, NavDrawer, SkipToContent) live here too. They test the rail, drawer and skip link in `BaseLayout`, which every page renders, so they have no test page of their own. Instead each one visits whichever page puts the layout in the state it checks: NavRail and NavDrawer visit a `/components/<id>` page so that "Components" is the current destination. What the site's rail and drawer can't show, an expandable rail or default backgrounds, is on the standalone pages of point 4 (`/tests/nav-rail-expandable`, `/tests/nav-drawer`).
6. **One smoke spec covers the docs pages.** `src/internal/DocsPages.spec.ts` visits every `/components/<id>` page, finding the ids from `src/docs/`'s folders so a new component is covered automatically, and lets the a11y fixture's axe scan run on each. An example that breaks accessibility is still caught, and an example that throws already fails the build. It sits in `src/internal/` beside `TableOfContents.spec.ts` because it tests the docs site rather than a component.

We rejected keeping the specs on the docs pages and marking the examples they depend on, for example with test ids in the examples. It would make the coupling visible, but examples would still be shaped by tests, and the docs would carry test markup readers can see in the source tab.

## Consequences

- Moving the existing specs is incremental work: one issue per spec under #78, each moving its spec to `src/tests/` in the same PR so a component spec still driving `/components/<id>` never sits there.
- A component's examples and its tests can drift apart: an example can show something no spec covers. The smoke spec only checks that each docs page renders and passes axe.
- Test pages gain test ids that readers checking them by eye can ignore. They're also still unchecked against the prop manifest, as ADR-0011 noted.
